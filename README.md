# CryptoBOT MVP

Безпечний прототип міжбіржового сканера Binance, Bybit, BingX і MEXC. Він використовує лише публічні ринкові API, не просить API-ключі та не виставляє ордери.

## Запуск

Найпростіше — двічі натиснути `start.bat`.

Або запустити вручну:

```powershell
python server.py
```

Після цього відкрийте `http://127.0.0.1:8765`.

## Docker

```powershell
Copy-Item .env.example .env
docker compose up -d --build
```

Панель навмисно публікується тільки на `127.0.0.1`. Для сервера використовуйте SSH tunnel або HTTPS reverse proxy з авторизацією — не відкривайте порт застосунку напряму в інтернет.

Перевірка стану:

```powershell
docker compose ps
docker compose logs -f cryptobot
```

Зупинка:

```powershell
docker compose down
```

## Структура коду

Логіка розбита на пакет `cryptobot/` (`config`, `scanner`, `funding`, `depth`,
`paper`, `risk`, `telegram`, `automation`, `app`). `server.py` лишається тонкою
точкою входу — `python server.py`, `start.bat` і Docker працюють як раніше.

## Автоматизація

За замовчуванням використовується `AUTOMATION_MODE=observe`: worker сканує ринок, але нічого не відкриває.

### demo / live

Режими `demo` і `live` вмикають двоноговий виконавець на `ccxt`
(`cryptobot/exchanges/`, `cryptobot/execution/`):

- `demo` — реальні API бірж у sandbox/testnet, гроші несправжні;
- `live` — реальні кошти, з твердими лімітами й kill-switch.

Потрібні API-ключі у `.env` (`BINANCE_API_KEYS`, `BYBIT_API_KEYS`,
`BINGX_API_KEYS` у форматі `key:secret`), щонайменше на 2 біржі. MEXC — заглушка
(немає futures API), тому автоматом не торгується. Без достатньої кількості
ключів `demo`/`live` тихо відкочуються в `paper` з попередженням у лог.

Що робить виконавець:

- `open_hedge` — дві market-ноги паралельно, звірка фактичних філів, `RECOVERY`
  при односторонньому виконанні, вирівнювання перекосу;
- `close_hedge` — reduce-only обидві ноги, реалізований PNL з фактичних цін;
- `startup_reconcile` на старті: розбіжність БД vs біржа → STOP + Telegram;
- monitor маржі: `MARGIN_WARN` → алерт, `MARGIN_CRITICAL` → аварійне закриття;
- тверді ліміти `LIVE_MAX_NOTIONAL_PER_POS` / `LIVE_MAX_TOTAL_NOTIONAL` /
  `LIVE_MAX_DAILY_LOSS_USDT`;
- `/api/live` — знімок live-позицій; кнопка `Закрити` та `lclose:<id>` у Telegram.

Автоматичного переказу коштів між біржами немає — розкидай капітал вручну.

### Нові пороги

- `PAPER_ENTRY_NET_PCT` за замовчуванням `0.30`;
- `DEPTH_GATE_MIN_NOTIONAL` (дефолт `2000`) — нижче цього обсягу перевірки
  заповнення стакана та прослизання не застосовуються;
- `FUNDING_ENTRY_BUFFER_MIN` (дефолт `10`) — вхід блокується, якщо до
  несприятливого нарахування фандінгу лишилось менше стількох хвилин;
- очікуваний фандінг тепер рахується за всі нарахування у вікні утримання
  (`FUNDING_INTERVAL_*_H`), а не як завжди один інтервал.

Для повністю автоматичного paper trading у `.env` встановіть:

```dotenv
AUTOMATION_MODE=paper
```

У цьому режимі worker сам:

- перевіряє чистий спред, фандінг, оборот і стакани;
- обирає найкращий маршрут серед усіх увімкнених бірж для кожного символу;
- звіряє доступність контрактів для API та відсіює несумісні номінали за відхиленням ціни;
- повторно перевіряє чистий спред після VWAP-прослизання;
- не дозволяє funding самостійно виправдати збитковий за ціною вхід;
- відхиляє зв’язку при недостатньому заповненні, прослизанні або надмірній концентрації маршруту;
- відкриває не більше `MAX_OPEN_POSITIONS` віртуальних позицій;
- закриває їх при сходженні спреду, paper Total Stop або максимальному часі утримання;
- записує рішення в `/app/data/cryptobot.db` у постійному Docker volume.

## Telegram

У `.env` можна вказати:

```dotenv
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
TELEGRAM_ALLOWED_USER_IDS=
```

Не надсилайте токен у чат і не комітьте `.env`. Після налаштування доступні команди `/status`, `/positions`, `/report`, `/pause`, `/resume`, `/stop`, `/resetstop` і `/help`. Команди приймаються лише з указаного чату й, якщо задано список, лише від дозволених Telegram user ID. Аварійний STOP зберігається після перезапуску, а `/resetstop` свідомо скидає його.

У режимі `observe` перевірений сигнал надходить із кнопками `Paper-вхід`, `Ігнорувати` і `Пауза`. У режимі `paper` позиція відкривається автоматично, а Telegram отримує повідомлення з кнопками `Закрити` та `Пауза`.

Щоб безпечно визначити ID:

1. Створіть `.env` із `.env.example` і додайте туди токен від BotFather.
2. Напишіть своєму боту `/start`.
3. Запустіть `python telegram_setup.py`.
4. Скопіюйте показані `chat_id` і `user_id` у `TELEGRAM_CHAT_ID` та `TELEGRAM_ALLOWED_USER_IDS` у `.env`.
5. Перезапустіть контейнер: `docker compose up -d --force-recreate`.

## Що вже рахується

- напрям LONG на дешевшій біржі та SHORT на дорожчій;
- gross spread за виконуваними bid/ask, а не за last price;
- чотири торгові комісії: дві ноги на вході та дві на виході;
- орієнтовний вплив одного інтервалу фандінгу;
- мінімальний 24-годинний оборот серед двох бірж;
- умовний результат для заданого депозиту.
- аналіз стаканів і виконуваний спред за VWAP для заданого обсягу;
- оцінка прослизання та відсотка заповнення двох ніг;
- коротка історія спреду, що накопичується під час роботи;
- відкриття, переоцінка й ручне закриття віртуальних paper-позицій;
- автономний фоновий сканер без відкритої вебсторінки;
- автоматичний paper-вхід і вихід за risk-порогами;
- SQLite audit-журнал і відновлення відкритих paper-позицій після перезапуску;
- постійна історія закритих угод і збереження аварійного STOP;
- статистика win rate, stop rate, profit factor, drawdown і формальні критерії готовності до demo;
- добовий Telegram-звіт та попередження про тривалу відмову ринкових даних;
- Telegram-команди та callback-кнопки з перевіркою chat/user ID.

## Перевірки

Запуск автоматичних тестів без доступу до біржових акаунтів:

```powershell
python -m unittest discover -s tests -v
```

Перехід до demo не відбувається автоматично. Команда `/report` покаже готовність лише після мінімум 50 закритих paper-угод, 7 днів спостереження, позитивного закритого PNL, допустимої частки стопів та справних даних обох бірж.

## Чого ще немає

- перевірки делістингів і специфікацій контрактів;
- WebSocket-потоків замість REST polling;
- реального Telegram webhook для публічного сервера;
- реального двоногого виконання й компенсації частково виконаного ордера.

До усунення цих пунктів термінал не слід використовувати з реальними коштами.
