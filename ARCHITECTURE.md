# Архітектура CryptoBOT

## Мета

Автономна серверна система міжбіржового арбітражу з мінімальним втручанням оператора. Telegram використовується як пульт і журнал подій, але ніколи не є єдиним джерелом рішення про угоду.

## Головний потік

```text
Internal Scanner ─┐
                  ├─> Signal Gateway -> Market Validator -> Risk Engine
Telegram Adapter ─┘                                      |
                                                         v
                              Paper -> Demo -> Guarded Live Executor
                                                         |
                                   Database <- Audit Log ─┘
                                                         |
                                                   Telegram Bot
```

1. `Signal Gateway` приймає внутрішні сигнали сканера або повідомлення дозволеного Telegram-каналу.
2. `Market Validator` повторно отримує bid/ask, стакани, фандінг, статус і специфікації контракту без довіри до тексту сигналу.
3. `Risk Engine` або відхиляє кандидата, або створює незмінний план угоди з терміном дії.
4. `Executor` одночасно виконує LONG і SHORT у режимі paper, demo або live.
5. `Position Supervisor` стежить за сходженням спреду, маржею, фандінгом, часом утримання та станом бірж.
6. Усі рішення записуються в журнал; Telegram отримує короткі повідомлення та кнопки керування.

## Режими безпеки

- `observe`: тільки сигнали й пояснення причин відхилення.
- `paper`: повністю автоматичні віртуальні входи та виходи.
- `demo`: реальні API бірж, але демоактиви.
- `guarded_live`: система готує план, оператор підтверджує його однією кнопкою протягом короткого TTL.
- `auto_live`: автоматичні угоди лише в межах попередньо заданого денного бюджету ризику.

Перехід на наступний режим виконується конфігурацією після окремого тестового періоду, а не автоматично.

## Telegram UX

### Сигнал

```text
🟡 CANDIDATE DEXEUSDT
LONG MEXC / SHORT Gate
Top spread: 1.24%
VWAP spread на 1 000 USDT: 0.91%
Net після витрат: 0.63%
Фандінг: прийнятний · Ліквідність: 100/100%
[Аналіз] [Paper-вхід] [Відхилити]
```

У режимі `paper` вхід відбувається автоматично, а повідомлення вже містить `[Закрити] [Пауза] [STOP]`.

### Команди

- `/status` — стан сервісів, позиції, PNL і денний ліміт.
- `/pause` та `/resume` — заборонити або дозволити нові входи.
- `/positions` — відкриті позиції.
- `/close_<id>` — закрити конкретну позицію.
- `/stop` — заборонити входи й запустити контрольоване закриття.

Команди приймаються лише від `TELEGRAM_ALLOWED_USER_IDS`. Callback обробляється ідемпотентно: повторне натискання не може створити другу угоду.

## Фільтри Risk Engine

- контракт існує та має статус `Trading` на обох біржах;
- збігаються базовий актив, тип контракту і розмір контракту;
- прогнозований net spread позитивний після чотирьох комісій, фандінгу й VWAP;
- обидві ноги можуть бути виконані на заданий обсяг;
- прослизання нижче `MAX_SLIPPAGE_PCT`;
- немає делістингу, аномального/подвійно несприятливого фандінгу або застиглого спреду;
- не перевищені ліміти позиції, символу, біржі, дня і загальної просадки;
- сигнал не прострочений і не дублюється;
- з’єднання, час системи та приватні потоки бірж справні.

## Виконання двох ніг

У demo/live режимі потрібна state machine:

```text
PLANNED -> LEG_A_PENDING + LEG_B_PENDING -> HEDGED -> CLOSING -> CLOSED
                    |                          |
                    └-> RECOVERY <-------------┘
```

Якщо виконується лише одна нога, `RECOVERY` негайно скасовує залишок і нейтралізує заповнену позицію. Звичайний повтор запиту заборонений без перевірки `clientOrderId`.

## Сервіси для серверного розгортання

Поточний MVP працює одним контейнером. Коли з’явиться demo executor, система розділяється на:

- `api`: вебінтерфейс і health endpoints;
- `worker`: сканер, validator, risk engine і supervisor;
- `telegram`: webhook/polling та callback-команди;
- `postgres`: угоди, сигнали, конфігурація й audit log;
- `redis`: короткі блокування, черги, TTL сигналів і distributed kill switch.

Для першого сервера достатньо одного `cryptobot` контейнера та постійного volume. Панель Compose прив’язана лише до `127.0.0.1`; віддалений доступ додається окремо через HTTPS reverse proxy з автентифікацією. Postgres і Redis додаються до переходу на demo/live.

## Секрети

- `.env` не комітиться;
- API-ключі створюються без права виведення коштів;
- live і demo використовують різні ключі;
- на сервері секрети передаються через Docker secrets або secret manager;
- жоден ключ чи Telegram token не повертається через API, UI або журнал.

## Умови переходу до demo

- щонайменше 14 днів безперервного paper-тесту;
- позитивний результат після всіх змодельованих витрат;
- відсутність необроблених односторонніх виконань;
- перевірені STOP, restart recovery і втрата з’єднання;
- окремий звіт за кожним символом та біржовою зв’язкою.
